### Вопросы для анализа

1. Чем поверхностная копия отличается от глубокой?

При поверхностной копии создается новый объект только верхнего уровня, а ссылки на все вложенные списки и их содержимое просто копируются. При глубоком копировании все объекты создаются заново.

2. Почему глубокое копирование не следует применять автоматически ко всем объектам?

Глубокое копирование потребляет много памяти, если объект большой и сложный. При наличии циклических ссылок классическая реализация глубокого копирования уйдет в бесконечную рекурсию, что вызовет переполнение стека - stack overflow.

3. В каких случаях достаточно поверхностной копии?

Поверхностной копии достаточно, если объект не содержит вложенных изменяемых объектов или вообще нужно менять параметры только верхнего уровня.


## Задание 3. Подсчет ссылок и время жизни объекта

Создадим `task_3.py` и импортируем модуль `sys`.

```python
import sys

data = [1, 2, 3]
print("После создания:", sys.getrefcount(data))

alias = data
print("После создания alias:", sys.getrefcount(data))

container = [data]
print("После помещения в контейнер:", sys.getrefcount(data))

del alias
print("После del alias:", sys.getrefcount(data))

container.clear()
print("После очистки контейнера:", sys.getrefcount(data))
```

Вывод:
```
После создания: 2
После создания alias: 3
После помещения в контейнер: 4
После del alias: 3
После очистки контейнера: 2
```

- почему `sys.getrefcount()` показывает на одну временную ссылку больше?

Так как сама передача объекта в качестве аргумента временно создает еще одну ссылку.

- какие инструкции увеличивают счетчик?

Присваивание объекта новой переменно, передача объекта в функцию как аргумент, добавление объекта в контейнер (список, множество, словарь, кортеж), само создание объекта

- какие инструкции уменьшают счетчик?

Явное удаление имени через `del`, переприсваивание переменной (-1, но +1 за счет появления нового объекта по этой ссылке), удаление объекта из контейнера, уничтожение самого контейнера


- почему `del alias` удаляет имя, а не командует напрямую удалить объект?

Если бы `del` удалял сам объект, то это бы сломало другие переменные, которые на него ссылаются.

Дополним программу экспериментом со слабой ссылкой. Для этого создадим простой класс-контейнер:
```python
import weakref


class Record:
    pass


record = Record()
weak_record = weakref.ref(record)

print(weak_record())
del record
print(weak_record())
```

Вывод:
```
<__main__.Record object at 0x0000020DB3B974D0>
None
```
Слабая ссылка в Python не продлевает время жизни объекта, потому что она не увеличивает его счетчик ссылок и не мешает уничтожить объект, если на него больше не указывают сильные ссылки.
Слабые ссылки могут пригодиться в ситуациях, когда нам нужно очищать кэш, если мы закончили работу с объектом, чтобы не нагружать память (и не держать там бесполезные объекты вечно).

### Вопросы для анализа

1. При каком условии подсчет ссылок позволяет освободить объект?

Объект освобождается в тот момент, когда количество ссылок на объект в памяти падает до нуля.

2. Всегда ли освобождение Python-объекта означает немедленный возврат памяти операционной системе?

Нет, освобождение объекта в Python означает, что память возвращается интерпретатору (CPython). Память для объектов в Python поделена на арены, пулы и блоки, если в арене есть хотя бы один существующий объект, то вся арена закреплена за процессом Python. 

3. Чем сильная ссылка отличается от слабой?

Сильная ссылка увеличивает счетчик ссылок объекта и удерживает его в памяти, тогда как слабая ссылка не увеличивает счетчик и позволяет сборщику мусора удалить объект, как только исчезнут все сильные ссылки.

### Вопросы для анализа

1. Как возникает циклическая ссылка?

Циклическая ссылка возникает тогда, когда два или более сложных объекта содержат ссылки друг на друга, образуя структуру, где каждый элемент ссылается на соседа.

2. Почему объект с ненулевым счетчиком ссылок иногда может быть недостижим из программы?

Это происходит из-за наличия циклических ссылок между объектами: даже после удаления всех внешних имен и переменных, связывающих их с программой, сами объекты продолжают ссылаться друг на друга, удерживая счетчик ссылок на уровне единицы, хотя к ним уже невозможно обратиться из кода.

3. Зачем сборщик мусора разделяет отслеживаемые объекты по поколениям?

Сборщик мусора разделяет отслеживаемые объекты по поколениям ради повышения производительности, так как свежие объекты нужно проверять часто, а старые можно реже (молодые объекты умирают чаще).

### Часть 2. Рост списка

Создадим пустой список и добавим в него 100 элементов. Выведем длину и размер списка только в тот момент, когда результат `sys.getsizeof()` изменился.
```python
my_list = []
prev_size = sys.getsizeof(my_list)
print(f"Длина: {len(my_list)}, Размер: {prev_size} байт")

for i in range(100):
    my_list.append(i)
    current_size = sys.getsizeof(my_list)
    if current_size != prev_size:
        print(f"Длина: {len(my_list)}, Размер: {current_size} байт, (+{current_size - prev_size})")
        prev_size = current_size
```

- увеличивается ли размер списка после каждого `append()`;

### Часть 3. Измерение через `tracemalloc`

С помощью `tracemalloc` сравним выделение памяти при создании:


```python

```
Вывод:
```

Peak memory:    3899.02 kB
```
и:
```python

```

Вывод:
```
Current memory: 0.08 kB
Peak memory:    0.08 kB
```

Сформулируем вывод о различии между материализованной последовательностью и объектом, который хранит правило получения значений.

Материализованная последовательность (`list`) при создании сразу выделяет в оперативной памяти место под все элементы и указатели на них, из-за чего её объем памяти прямо пропорционален количеству элементов. В то же время объект `range` представляет собой итератор, который хранит исключительно правило генерации (стартовое значение, границу и шаг). Поэтому `range` занимает фиксированный и минимальный объем памяти.
